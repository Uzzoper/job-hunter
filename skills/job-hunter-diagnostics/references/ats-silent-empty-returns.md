# ATS Providers — Silent Empty Returns

> Greenhouse/Ashby/Lever providers return 0 jobs with **no WARN or ERROR** in logs. Investigation from 2026-09-23.

## Symptom

Fetch result shows:
```
greenhouse: fetched 0 raw jobs, normalized 0
ashby: fetched 0 raw jobs, normalized 0
lever: fetched 0 raw jobs, normalized 0
```

But:
- ATS providers ARE registered and executed (INFO logs appear: `total unique jobs fetched: 0`)
- JAR contains correct config (verified via `docker cp` + `jar xf`)
- APIs respond via `curl` from inside the container (HTTP 200, 402 jobs for Stone board)
- No "skipping board" WARN in logs (which would indicate an exception in the board loop)

## Unresolved root cause

Two hypotheses remain:
1. **Query string encoding**: `RestClient.uri(String path)` *may* encode `?` as `%3F` — but Gupy uses the same `RestApiStrategy.extractWithPath()` pattern and works, so this is unconfirmed for ATS.
2. **Mapper returns null**: `GreenhouseProvider.mapNode()` may return null for all nodes (blank title or URL) — but the debug log `fetched N jobs for board X` is at DEBUG level and won't appear in production logs.

## Diagnostic steps for ATS silent failures

1. Verify the JAR has the expected config (see "JAR inspection" below).
2. Confirm the INFO line appears (provider executed, returned 0).
3. Check there's NO "skipping board" WARN (which would indicate an exception in the board loop).
4. If no WARN: enable DEBUG logging temporarily or add a temporary WARN log inside `GreenhouseProvider.extract()` to see the actual API response size.
5. Test the exact API URL with `curl` from inside the container.

## JAR inspection — verify embedded Spring Boot config

When you suspect the running JAR doesn't match the source tree:

```bash
# Copy JAR out of the running container
docker cp job-hunter-backend:/app/app.jar /tmp/app-inspect.jar

# Extract the embedded application.yaml
cd /tmp && jar xf app-inspect.jar BOOT-INF/classes/application.yaml

# Inspect
cat BOOT-INF/classes/application.yaml | grep -A10 "^ats:"
```

The JAR packages `src/main/resources/application.yaml` as `BOOT-INF/classes/application.yaml` (Spring Boot fat JAR layout). Docker Compose `build: .` rebuilds from the current source tree, so a stale `target/` is not the issue — but the JAR may be stale if `docker compose up -d` was run without `docker compose build` after a source change.

## Key finding (2026-09-23)

The `RestClient.uri(path)` encoding hypothesis was **partially disproven**: Gupy uses the same pattern and works. The actual root cause was **not found** after extensive investigation. The session ended with the user asking to move on.
